# 二、数据库设计

## 2.1 为什么选 MongoDB

先把需求里几个会影响表结构的点列出来：

1. 每份问卷的题目数量不固定，题型不同，附加参数也不同。单选题有选项，多选题还有最少/最多选择数，数字题有范围，文本题有字数限制。
2. 跳转规则是“满足什么条件就跳到哪道题”，数量不固定，条件类型也不一样。
3. 一次填写产生的若干条答案天然属于同一个整体，通常一起写入、一起读出来做统计。
4. 统计要按问卷、按题目分组，聚合比较多。

如果放进关系型数据库，题目参数要么拆成很多张表（单选选项表、多选参数表、数字参数表），要么用一张宽表加很多可空字段，要么走 EAV。第一种 join 太多，第二种字段含义不稳定，第三种查起来很别扭。跳转规则更麻烦，条件类型和参数没法用固定的列表示。

MongoDB 的文档模型刚好适合这种“结构随业务变化”的数据。题目的参数直接放在题目文档里，不同题型放不同子文档，没有的字段就不出现。跳转规则是题目文档里的数组，一条规则就是一个对象。一次填写的答案作为数组放在响应文档里，写入是一条 insert，统计时 unwind 展开即可。

需要说明的是，选 MongoDB 不是因为“不用设计表结构”，而是把设计从表结构转移到了文档边界、字段校验和索引上。这个项目的集合划分、JSON Schema 校验器和索引都写在 `scripts/init-db.js` 里。

## 2.2 集合划分

系统一共八个集合：`users`、`surveys`、`questions`、`responses`、`question_roots`、`question_versions`、`question_banks`、`bank_items`。

前四个是第一阶段的，后四个是第二阶段做题目复用和版本管理时加的。第三、四节先写第一阶段的结构，2.9 开始补第二阶段为什么加、怎么加。

没有把所有东西塞进一个集合。原因很直接：用户、问卷、题目、回答的读写方式和生命周期完全不同。用户按用户名查，问卷按创建者查，题目按问卷查，回答按问卷查和聚合。混在一起会让索引和校验规则互相干扰，也没法给不同文档设置不同的必填字段。

也没有把题目嵌在问卷文档里。一开始考虑过 `surveys.questions: [...]` 这种写法，看起来更“文档”，但很快发现问题：

- 跳转规则要引用题目 id，回答里也要记录题目 id。题目嵌在问卷里虽然也能生成子文档 id，但更新某一道题时要读写整个问卷文档。
- 第二阶段很可能会加题目、改题目。独立集合可以只改一条题目文档，冲突范围小。
- 统计接口需要按 `surveyId` 和题目 id 查 responses，题目本身独立出来更好对应。
- 题目多了以后，问卷文档会变大，而且题目顺序、唯一性约束不好在数组里保证。

代价是查询问卷详情时多一次 `questions.find({surveyId})`。这个代价很小，而且题目本来就要按 order 排序，独立集合正好可以建联合索引。

## 2.3 各集合字段

### users

```json
{
  "_id": ObjectId("..."),
  "username": "student01",
  "passwordHash": "scrypt$salt$hash",
  "createdAt": ISODate("2026-10-20T10:00:00Z"),
  "lastLoginAt": ISODate("2026-10-21T08:00:00Z")
}
```

`passwordHash` 里存的是 `scrypt$盐$哈希`，盐是随机生成的，每个用户不同。没有存明文密码，也没有把盐单独放一个字段，这样一条用户文档就够校验了。

`lastLoginAt` 不是需求要求的，是登录时顺手更新的，方便以后做“最近登录”之类的功能，现在页面上没展示。

### surveys

```json
{
  "_id": ObjectId("..."),
  "ownerId": ObjectId("用户id"),
  "title": "健康状况小调查",
  "description": "麻烦大家抽两分钟填一下",
  "allowAnonymous": true,
  "status": "published",
  "deadline": ISODate("2026-11-01T16:00:00Z"),
  "createdAt": ISODate("2026-10-20T10:00:00Z"),
  "publishedAt": ISODate("2026-10-20T10:05:00Z"),
  "closedAt": null
}
```

`status` 只有三个值：`draft`、`published`、`closed`。发布和关闭都通过改状态完成，没有单独建“问卷状态历史”集合。需求没有要求记录状态变更历史，所以没做。

`deadline` 和两个时间戳允许为 null。JSON Schema 里写成 `bsonType: ["date", "null"]`。

### questions

```json
{
  "_id": ObjectId("..."),
  "surveyId": ObjectId("问卷id"),
  "rootId": ObjectId("题目本体id"),
  "versionId": ObjectId("版本id"),
  "versionNo": 2,
  "fromBank": true,
  "frozen": false,
  "order": 3,
  "type": "number",
  "title": "你的年龄",
  "required": true,
  "options": [],
  "multiple": { "minSelect": null, "maxSelect": null },
  "text": { "minLength": null, "maxLength": null },
  "number": { "min": 0, "max": 120, "integer": true },
  "jumps": [
    {
      "targetQuestionId": ObjectId("题目id"),
      "match": { "kind": "number", "op": "==", "value": 100 }
    }
  ],
  "createdAt": ISODate("...")
}
```

`rootId`、`versionId`、`versionNo` 是第二阶段加的，具体原因见 2.9。题目内容在这里仍然存了一份完整快照，这是故意的：填答、跳转判断、统计都只读这一个集合，不用每道题都回查版本表。代价是同一份内容存两遍，但一道题的内容只有几百字节，换来的是查询路径简单。

这里做了一个取舍：四种题型的参数子文档都保留，只是不适用的字段为 null 或空数组。这样读取题目的代码不用判断“这个字段存不存在”，校验器也能统一写。代价是文档里有一些空字段，但一道题最多多几十字节，可以接受。

另一种做法是只写当前题型需要的字段，文档更干净，但前端和后端每处都要判空。考虑到题型只有四种，字段也不算多，最后选了统一结构。

`options` 用 `{key, label}` 而不是纯字符串，原因是跳转规则要引用选项。如果按选项文字引用，创建者改一下文字，已有跳转规则就失效了。加了 key 以后，文字随便改，规则还指向原来的 key。key 由服务端生成，默认 A、B、C，也可以由前端传已有的 key。

`jumps` 是数组，每条规则包含判断条件和目标题目 id。条件有两种：

- `{kind: "option", keys: ["A"], mode: "any"}`：选中的选项包含 A。`mode: "all"` 表示 keys 全部被选中，主要给多选题用。
- `{kind: "number", op: "==", value: 100}`：数字题的答案和 100 比较，op 支持 `==`、`!=`、`>`、`>=`、`<`、`<=`。

没有把跳转规则单独建集合。规则总是跟着某道题走，单独建集合要多一次查询，也失去了“题目和规则一起改”的原子性。

### responses

```json
{
  "_id": ObjectId("..."),
  "surveyId": ObjectId("问卷id"),
  "respondentId": ObjectId("用户id") 或 null,
  "anonymous": false,
  "submittedAt": ISODate("..."),
  "path": [ObjectId("题目1"), ObjectId("题目3")],
  "answers": [
    { "questionId": ObjectId("题目1"), "type": "single", "optionKeys": ["A"], "value": null, "numberValue": null },
    { "questionId": ObjectId("题目3"), "type": "text", "optionKeys": [], "value": "多加点实操", "numberValue": null }
  ]
}
```

答案内嵌在响应文档里，没有单独建 `answers` 集合。理由：

- 一次提交是一个整体，要么全部写进去，要么都不写。内嵌数组一条 insert 就完成了。
- 统计时按问卷取出响应，再 unwind 答案，正好符合 MongoDB 的聚合方式。
- 一次填写最多几十道题，数组不会把文档撑大，也远低于 16MB 限制。
- 如果答案独立成集合，查一次填写要 join 回响应，查统计要按 surveyId 扫大量答案文档，反而更慢。

如果以后要做“同一题所有问卷的横向分析”，答案独立集合会更合适。但那是另一个需求，现在没必要提前拆。

`respondentId` 在匿名提交时写成 null，而不是“存了但不展示”。匿名的意义是系统也不应该知道是谁填的，所以干脆不保存。非匿名提交会保存用户 id，方便以后查“我填过哪些”。

`path` 记录实际经过的题目顺序。统计本身不依赖它，但调试跳转时很有用：出问题时可以直接看出服务端实际走了哪几道题。它也算一点冗余，因为从 answers 的 questionId 能推出来大部分信息，不过被跳过但没作答的题只能靠 path 看出来，所以保留。

答案里同时有 `optionKeys`、`value`、`numberValue`，也是统一结构。选择题只填 optionKeys，文本题只填 value，数字题只填 numberValue。查询时用哪个字段很清楚。

## 2.4 集合之间的关系

`surveys.ownerId` 引用 `users._id`，`questions.surveyId` 引用 `surveys._id`，`responses.surveyId` 引用 `surveys._id`，`responses.respondentId` 引用 `users._id`，`jumps.targetQuestionId` 引用 `questions._id`。

MongoDB 不强制外键，所以这些关系由应用层保证：

- 创建问卷时 ownerId 直接取 session 里的用户 id。
- 加题目、改题目、删题目之前先确认问卷属于当前用户。
- 跳转目标必须是同一份问卷里已经存在的题目，不能指向自己。
- 删除题目时，同时把其他题目里指向它的跳转规则 `$pull` 掉。这一点在测试里有专门用例。

没有做“删除用户时级联删除问卷”。现在系统没有删除用户的功能，等真加了再说。

## 2.5 校验规则和索引

集合创建时会写入 `$jsonSchema` 校验器，服务启动或执行 `npm run init-db` 时通过 `collMod` 更新。校验器主要管类型、枚举、长度和必填字段，业务规则（比如“最少选择数不能大于最多选择数”“跳转目标必须存在”）放在应用层，因为要用到其他文档。

索引如下：

| 集合 | 索引 | 作用 |
| --- | --- | --- |
| users | `{username: 1}` 唯一 | 登录查询、防止重复注册 |
| surveys | `{ownerId: 1, createdAt: -1}` | 我的问卷列表，按创建时间倒序 |
| questions | `{surveyId: 1, order: 1}` 唯一 | 按问卷取题目并按顺序返回，同时防止 order 重复 |
| responses | `{surveyId: 1, submittedAt: -1}` | 统计时按问卷取回答 |
| responses | `{surveyId: 1, respondentId: 1}` | 给“查某人是否填过”留的，本阶段没用到 |
| responses | `{surveyId: 1, answers.questionId: 1}` | 统计按题目过滤答案，多键索引 |

`{surveyId: 1, respondentId: 1}` 现在确实没被查询用到。保留是因为第二阶段很可能要限制重复填写，到时候直接查这个索引即可。如果严格按“不为假设需求设计”的原则，可以删掉，但一条索引的成本很低，这里保留并说明用途。

## 2.6 没有使用的冗余

没有在 `surveys` 里存 `questionCount`，也没有存 `responseCount`。列表页需要这两个数字，现在的做法是按当前用户的所有问卷 id 做两次分组聚合，再拼到返回结果里。数据量是课程作业级别，这样完全够。

存冗余计数字段的问题是：加题目、删题目、有人提交时都要记得更新，任何一处漏了就会出现数字和实际不一致。问卷被关闭、回答被删除（现在没有删除回答的功能）时也要维护。与其承担这个风险，不如查询时算。

同样，`responses` 里没有冗余填写人的用户名。用户改名后冗余字段会过期，需要用户 id 再查一次即可。统计页也不需要显示填写人。

## 2.7 逻辑没有写死在代码里

跳转规则存在 `questions.jumps` 里，服务端有一个通用的 `nextQuestion` 函数按规则计算下一题，代码里没有“如果第 1 题选 A 就跳第 5 题”这种硬编码。新增一条规则只需要改数据，不需要改代码。

题型参数也一样。数字题的范围、文本题的字数、多选题的数量限制都从题目文档里读，校验函数按 `type` 分派，不针对某道具体题目写判断。

不过要说清楚，新增一种题型仍然需要改代码：加校验函数、加前端输入控件、加统计分支。这是题型本身的逻辑，不是某份问卷的业务规则，放在代码里是合理的。

## 2.8 和关系型设计的对比

如果硬要用关系型数据库，大致会是这样：

- users、surveys、questions 三张主表；
- question_options 存选项；
- question_rules 存跳转规则，条件和值用字符串或 JSON 字段；
- responses 存一次提交；
- answers 存每条答案，还要按题型分列或再加子表。

能实现，但表多、join 多，题目参数和跳转条件仍然要借助 JSON 列或 EAV。MongoDB 把题目参数和答案直接放在文档里，代码和查询都短一些。这个项目的题型和跳转规则变化比较频繁，文档模型的收益比较明显。

## 2.9 第二阶段为什么改了题目模型

第二阶段的要求可以归成三句话：

1. 题目要能存起来反复用，一道题出现在多份问卷里；
2. 改题目不能把已经做好的问卷改坏；
3. 要能看见这道题以前长什么样、被谁用过、不同问卷里用的是哪一版。

如果还按第一阶段的写法，题目内容直接挂在 `questions` 文档上，第二条就做不到。同一道题在 A、B 两份问卷里是两条独立文档，改 A 的那条不会影响 B，看起来没问题；但这样一来“同一道题”这个概念就没了，统计没法跨问卷合并，也谈不上版本。

真正麻烦的是第三种情况：A、B 共用一道题，后来只想改 A。如果两条文档指向同一份内容，改一处就会影响另一处；如果各存各的，又回到了“没有共同身份”的老问题。

最后的做法是把“题目”拆成两层：

- `question_roots` 只表示“这是同一道题”，存创建者、当前最新版本指针、共享名单；
- `question_versions` 存具体内容，每次修改插入一条新文档，旧文档不动；
- `questions` 是“某份问卷里的这道题”，指向一个具体版本，并保存一份内容快照。

这样 A 想改，就基于它当前用的版本再生成一个新版本，A 指过去；B 还指着老版本，什么都不用做。两份问卷里的题目仍然是同一个 root，所以统计能合到一起。

## 2.10 版本表为什么只增不改

`question_versions` 里没有任何更新接口，只插入。连“恢复旧版本”也不是把指针拨回去，而是把旧内容复制出来存成一个新版本。

这么做有两个好处：

- 历史是完整的。任何时候看到的版本列表，就是这道题真实经历过的东西，不会因为一次恢复就少一段。
- 已发布问卷绝对不会被影响。已发布问卷的题目指向某个版本 id，只要版本文档不变，它看到的内容就不会变。

代价是版本会越攒越多。一门课的大作业里，一道题改十几次也就十几条文档，完全可以接受。如果真到了需要清理的量级，可以按“没有问卷引用且不是最新版”的规则归档，但现在没必要提前做。

另外，版本号用的是 `root.latestVersionNo + 1`，不是全局自增。并发下两个人同时改同一道题，理论上会算出同一个版本号。`{rootId, versionNo}` 上建了唯一索引，后写入的那条会直接报错，不会悄悄覆盖。课程作业的场景里基本碰不到，但索引兜住了最坏情况。

## 2.11 新集合字段

### question_roots

```json
{
  "_id": ObjectId("..."),
  "ownerId": ObjectId("用户id"),
  "latestVersionId": ObjectId("版本id"),
  "latestVersionNo": 3,
  "sharedWith": [ObjectId("被共享用户id")],
  "createdAt": ISODate("..."),
  "updatedAt": ISODate("...")
}
```

`latestVersionNo` 是冗余的。正常可以靠 `latestVersionId` 查出版本号，但列表页要显示“v3”，每题都回查一次版本表不划算，所以存了一份。它只在新增版本时改，改动点只有一个，不容易写漏。

`sharedWith` 直接放数组，没建单独的共享表。共享关系很简单：谁能看、谁能用。查询也就是 `{sharedWith: 当前用户}`，数组上建多键索引即可。以后如果要记录“谁在什么时候共享给谁”，再拆表也不迟。

### question_versions

```json
{
  "_id": ObjectId("..."),
  "rootId": ObjectId("题目本体id"),
  "ownerId": ObjectId("用户id"),
  "versionNo": 2,
  "parentVersionId": ObjectId("上一版id"),
  "source": "fork",
  "changeNote": "在问卷中修改",
  "type": "single",
  "title": "你常用的编程语言",
  "options": [{ "key": "A", "label": "Java" }],
  "multiple": { "minSelect": null, "maxSelect": null },
  "text": { "minLength": null, "maxLength": null },
  "number": { "min": null, "max": null, "integer": false },
  "createdAt": ISODate("...")
}
```

`parentVersionId` 记录这一版是从哪一版改出来的，界面上显示的“由 v1 改出”就是读这个字段。`source` 区分四种来源：新建、修改、分叉、恢复。恢复时 parent 指向被恢复的那一版，所以能看出“v5 是从 v2 恢复来的”。

版本里**不存** `required` 和 `jumps`。这两个东西是问卷层面的：同一道题在 A 卷必答、在 B 卷选答很正常；跳转目标更是只在本卷里有意义。把它们塞进版本，复用的时候反而要清理。

### question_banks 和 bank_items

```json
// question_banks
{ "_id": ObjectId("..."), "ownerId": ObjectId("..."), "name": "课程评价常用题", "description": "…", "createdAt": ISODate("..."), "updatedAt": ISODate("...") }

// bank_items
{ "_id": ObjectId("..."), "bankId": ObjectId("..."), "rootId": ObjectId("..."), "addedAt": ISODate("...") }
```

题库和题目是多对多：一道题可以放进多个题库，一个题库有很多题。所以用了中间集合 `bank_items`，并在 `{bankId, rootId}` 上建唯一索引，防止同一道题在一个题库里重复出现。

没有把题库做成 `root.bankIds` 数组。那样“删题库”要遍历所有题目去 pull，而且题目加入多个题库后数组会一直变长。中间集合删起来就是一条 deleteMany。

## 2.12 共享的边界

共享的是“题目”，不是“版本”。被共享的人能看到这道题的所有版本，也能把它用到自己的问卷里，但不能修改、不能删除、不能改共享名单。判断逻辑集中在 `question-catalog.js` 的 `loadAccessibleRoot` 和 `loadOwnedRoot` 两个函数里，路由只负责调用。

统计接口用的是 `loadAccessibleRoot`，但聚合时只取当前用户名下的问卷。也就是说，别人共享给你的题，你只能看到自己问卷里的回答，看不到对方问卷的数据。这一点在文档和页面上都写明了，避免误解。

## 2.13 索引补充

| 集合 | 索引 | 作用 |
| --- | --- | --- |
| question_roots | `{ownerId: 1, updatedAt: -1}` | 我的题目列表，按最近修改排序 |
| question_roots | `{sharedWith: 1}` 多键 | 查“共享给我的题目” |
| question_versions | `{rootId: 1, versionNo: 1}` 唯一 | 按题目取版本历史，同时防止版本号重复 |
| questions | `{rootId: 1, surveyId: 1}` | 查一道题被哪些问卷使用、跨问卷统计 |
| question_banks | `{ownerId: 1, createdAt: -1}` | 我的题库列表 |
| bank_items | `{bankId: 1, rootId: 1}` 唯一 | 题库内题目去重、按题库取题 |

`questions` 上原来的 `{surveyId: 1, order: 1}` 唯一索引保留，它保证同一份问卷里题号不重复。新加的 `{rootId: 1, surveyId: 1}` 是给“使用情况”和跨问卷统计用的，两个索引职责不重叠。

## 2.14 第一阶段的数据怎么办

第一阶段已经建过问卷的话，那些题目文档里没有 `rootId`。校验器新加了必填字段，直接改这些文档会报校验错误。

处理方式是 `scripts/migrate-v2.js`：给每道没有 `rootId` 的老题补一个 root 和一个 v1 版本，再把 `questions` 上的三个字段填上。补完之后老问卷照常能填、能统计，只是这些题也顺带进了题目库。

脚本是幂等的，只处理 `rootId` 不存在的文档，重复执行不会重复建版本。执行顺序是 `npm run init-db` 再 `npm run migrate-v2`，因为迁移脚本自己也会先跑一遍集合初始化。
