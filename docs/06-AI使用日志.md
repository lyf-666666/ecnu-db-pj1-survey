# 六、AI 使用日志与说明

## 6.1 使用记录

工具：Trae（对话里用的模型是 DeepSeek）。整个过程是边做边问，不是一次生成整个项目。下面按阶段记录，提示词写的是大意，不是逐字复制。

### 记录 1：需求梳理和集合划分

提示词（大意）：

> 这是我课程作业的需求文档。先不要写代码，帮我分析一下数据应该怎么分集合。重点考虑题目类型不固定、跳转规则要配置、回答要统计这几个点。

得到的结果：AI 给了三种方案，一种是把题目嵌在问卷里，一种是题目独立集合，一种是题目和答案都独立。还列了关系型数据库会遇到的问题。

我的修改：选了题目独立成集合的方案。理由是跳转规则和回答都要引用题目 id，嵌在问卷里更新起来别扭。回答仍然内嵌在 responses 文档里，没有单独拆 answers 集合，因为一次填写是一个整体。这个取舍在数据库设计文档里写了。

### 记录 2：集合校验器和索引

提示词（大意）：

> 按刚才定的四个集合，写 MongoDB 的 JSON Schema 校验器和索引，用原生驱动，不要 Mongoose。

得到的结果：`scripts/init-db.js` 的初版，包含 users、surveys、questions、responses 四个集合和几个索引。

我的修改：

- 给 `deadline`、`publishedAt`、`closedAt` 加上 `["date", "null"]`，因为创建时这些字段可能是空。
- 题目文档统一保留 `multiple`、`text`、`number` 三个子对象，不适用的字段写 null 或空数组，避免读取时到处判空。
- 补了 `{surveyId: 1, "answers.questionId": 1}` 这个多键索引。一开始只按 surveyId 建了索引，后来看统计管道会按题目过滤，就加上了。
- 把初始化改成 `collMod`，这样重复执行 `npm run init-db` 不会因为集合已存在而跳过校验器更新。

### 记录 3：跳转逻辑

提示词（大意）：

> 跳转规则存在题目里，怎么保证客户端不能绕过？必答题被跳过的时候不能误报。

得到的结果：AI 第一版是让前端算下一题，后端按顺序检查所有必答题。

我的修改：这个思路有问题，被跳过的必答题会被误判。改成服务端从第一题重放路径，按 jumps 计算下一题，只校验实际经过的题目。客户端多传的答案直接忽略。代码在 `src/services/answer-check.js`。另外加了 visited 集合检测循环，避免 1→3、3→1 这种配置把请求卡死。

还有一个细节是 AI 最初把 path 只记录有答案的题，我改成记录实际经过的所有题，包括跳过去但没有作答的选答题。这样调试时能看出路径到底怎么走的。

### 记录 4：题目配置校验

提示词（大意）：

> 创建和修改题目时要把不合法的配置拦住，比如选项 key 重复、多选最少大于最多、跳转目标不存在。

得到的结果：`src/services/question-check.js`。

我的修改：

- 选项 key 不传时按 A、B、C 自动生成，传了要检查重复和格式。
- 跳转目标限制在同一问卷内，不能指向自己。
- 删除题目时补了一段 `$pull`，把别的题目里指向它的规则清掉。AI 的初版只删了题目，没管跳转，这个在测试 T13 里专门验证。

### 记录 5：前端页面

提示词（大意）：

> 用原生 HTML 和 JS 做五个页面，不要框架，样式简单一点。

得到的结果：`public/` 下的五个页面和脚本。

我的修改：

- AI 初版用 `form.title`、`form.min` 这种写法读表单值。`title` 和 `min` 在表单元素上是容易和内置属性混淆的名字，我改成 `form.elements.title`，避免不同浏览器行为不一致。
- 切换题型时，旧的跳转规则控件还留在页面上，读取时会去拿不存在的 `.jump-op`。改成切换题型先清空规则区，再重新渲染。
- 填写页加了本地校验，体验好一点。但服务端校验没有省，前端只是提示。
- 发布后把编辑区隐藏，题目列表只读。这个规则是后来加的，AI 初版允许发布后继续改题，会导致历史回答和题目对不上。

### 记录 6：测试

提示词（大意）：

> 按需求里的六类测试写自动测试，用 node:test 和 supertest，数据库用内存 MongoDB。

得到的结果：`tests/api.test.js` 初版。

我的修改：

- AI 写的测试用 `findOne({ _id: body.responseId })` 查响应，但接口返回的是字符串，MongoDB 要 ObjectId。查出来一直是 null，改成 `new ObjectId(...)`。
- 有一条测试让第 2 题只选一个选项，但题目要求最少两个，请求本身就是非法的。改成选 A、C。
- 跳转测试原来断言 path 只包含有答案的题，和服务端“记录所有经过的题”的语义不一致，改成了实际路径。
- 补了“不允许匿名时拒绝匿名提交”和“删除题目清理跳转”两个用例。AI 初版没有这两个。

### 记录 7：文档

提示词（大意）：

> 根据代码和测试结果整理文档，写得像学生自己写的，不要空话。

得到的结果：各文档的初稿。

我的修改：删掉了一些很大的词，比如“高效”“赋能”“显著提升”这类没信息量的表述。数据库设计里补了实际的取舍过程，比如为什么题目不嵌在问卷里、为什么统计不存冗余。测试文档里的数字都是从实际运行结果抄的，没有编。

### 记录 8：第二阶段的需求拆解

提示词（大意）：

> 第二阶段要求题目能复用、能共享、改题不能影响已发布问卷、还要有版本历史。先说清楚这些要求之间有没有冲突，再给方案，不要直接写代码。

得到的结果：AI 列了三种做法。一种是复制题目，改一份不影响另一份；一种是题目只保存一份，所有问卷共享；一种是题目本体加不可变版本。还指出“复制”做不到跨问卷统计，“共享一份”做不到只改某一份问卷。

我的修改：选了第三种。前两种都能满足其中一部分要求，但没法同时满足“同一道题”和“各自独立的版本”。这个判断过程写进了数据库设计 2.9。AI 最初的方案里，版本表还带着 `required` 和 `jumps`，我让它们留在问卷的题目文档上，因为同一道题在不同问卷里必答/选答可以不一样，跳转更是只对本卷有意义。

### 记录 9：版本接口的实现

提示词（大意）：

> 按刚才的模型实现版本相关的接口，注意恢复旧版本不能真的把指针拨回去，已发布问卷引用的版本必须保持不变。

得到的结果：`src/services/question-catalog.js` 和 `src/routes/questions.js`。

我的修改：

- AI 初版把 `parentVersionId` 默认设成最新版本。我改成在问卷里改题时指向“这份问卷当前用的版本”，不然版本链会看不出分叉是从哪来的。
- 有一处 `updateOne` 写成了 `{ $set: update, $set: { jumps: [] } }`。JavaScript 对象字面量里同名 key 后一个会覆盖前一个，结果题目内容全丢了，只剩 jumps。改成 `{ $set: { ...update, jumps: [] } }`。
- 新增版本时本来想“只有父版本是最新版才更新 latestVersionId”，后来改成总是更新。题库列表显示“最近创建的版本”更符合直觉，旧问卷反正不受影响。

### 记录 10：跨问卷统计

提示词（大意）：

> 同一个题目不同版本的选项编号可能对不上，跨问卷统计按什么合并？给我一个能说清楚限制的做法。

得到的结果：AI 建议按选项编号合并，并给了一段聚合管道。

我的修改：按编号合并是错的。v1 的 A 可能是“Java”，v2 的 A 可能变成“Python”，合在一起会得出完全错误的结论。改成按选项文字合并。代价是改过文字的选项会被算成两项，这个限制写在了统计接口说明和 4.11 里，没有藏着。

另外 AI 的聚合管道里用 `$group` 一次算完，但每道题的选项映射不一样，硬写管道会非常难读。改成先筛出答案，再在 JS 里循环累加。数据量小的时候这样更清楚，也方便以后加题型。

### 记录 11：第二阶段的前端和测试

提示词（大意）：

> 加一个题目库页面，能建题、看版本、看使用情况、共享、看跨问卷统计；问卷编辑页要能从题库选题，还要提示有新版本。

得到的结果：`public/questions.html`、`public/js/questions.js`，以及编辑页的选题面板。

我的修改：

- 选题面板最初只显示最新版。后来补了一次详情请求，把版本下拉做出来，不然“同一题不同版本共存”在界面上没法操作。
- 切换版本会清空跳转规则。这个不是 AI 提的，是我在写 `sync` 时想到的：选项编号可能变了，旧规则会指向不存在的 key。
- 测试初版跑出 500，原因是 `stats.js` 用了 `ObjectId` 但没 require。补上后通过。
- 测试里预期“题库里最新是 v4”，实际是 v5，因为恢复旧版本也会产生新版本。这个数字我按实际结果改了，没有改代码去迁就测试。

## 6.2 AI 使用说明

### AI 帮了什么

项目骨架、八个集合的初版结构和索引、账号和问卷的 CRUD 接口、四种题型的校验函数、版本和共享的接口、统计聚合、六个页面、25 个接口测试、文档初稿，基本都是 AI 先出的版本。没有 AI 的话，这些重复性的代码要写很久。

### AI 做错了什么

比较明显的有六处：

1. 跳转逻辑一开始放在前端算，后端只按顺序检查必答题，导致被跳过的必答题误报。
2. 测试用字符串去查 ObjectId，查询永远是 null，测试一直失败。
3. 前端用 `form.title` 这种写法读表单，遇到和内置属性同名的字段有风险。
4. 删除题目时没有清理其他题目里指向它的跳转规则。
5. 版本表初版把 `required` 和 `jumps` 也放了进去，复用时会带到别的问卷里。
6. 一个 `updateOne` 里写了两个 `$set`，后一个把前一个覆盖掉，字段会静默丢失。这个是在读代码时发现的，没等到运行。

另外 AI 写文档时喜欢用很整齐的排比和“首先、其次、最后”，读起来不像人写的，这部分我重写了不少。

### 自己改了什么

上面每一条“我的修改”都是实际动过的地方。第二阶段改动主要集中在版本模型的选择、父版本的指向、跨问卷统计的合并口径、切换版本时清空跳转，以及新增的前端交互。

### 自己设计了什么

第一阶段的四个集合，以及第二阶段的题目本体、版本、题库、题库条目四个集合，都是我在几个候选方案里比过之后定下来的。题目参数统一结构、回答内嵌、跳转规则跟着题目走、匿名提交不保存用户 id、统计不存冗余而是现算，这些也来自同一轮取舍。第二阶段的“题目本体 + 不可变版本 + 问卷引用具体版本”是三选一，理由写在数据库设计 2.9。AI 提供的是候选和实现，选哪个、为什么选，是我自己定的。
