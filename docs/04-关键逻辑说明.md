# 四、关键逻辑说明

这一部分写清楚三件事：跳转怎么算、答案怎么校验、统计怎么来。代码主要在 `src/services/answer-check.js`、`src/services/question-check.js` 和 `src/services/stats.js`。

## 4.1 跳转规则怎么存

每条规则挂在某道题目上，存在 `questions.jumps` 数组里。一条规则由两部分组成：`match` 是条件，`targetQuestionId` 是目标题目。

条件有两种：

```json
{ "kind": "option", "keys": ["A"], "mode": "any" }
{ "kind": "number", "op": "==", "value": 100 }
```

选项条件的 `mode` 有两种。`any` 表示选中的选项里只要有一个在 `keys` 中就算满足；`all` 表示 `keys` 里的选项必须全被选中。单选题一般用 `any`，多选题可以选 `all`，比如“同时选了苹果和香蕉就跳到第 5 题”。

数字条件支持 `==`、`!=`、`>`、`>=`、`<`、`<=`。文本框不支持跳转，需求里只要求单选、多选和数字填空。

一份题目可以配多条规则，服务端按数组顺序检查，第一条满足的生效。都不满足就按 order 进入下一题。

## 4.2 服务端重放路径

一开始我想得比较简单：前端算好下一题，提交时按顺序检查所有必答题。后来发现有问题。假设第 1 题选 A 跳到第 5 题，第 2、3、4 题都是必答，按顺序校验就会报“必答题没回答”，但这几道题根本没出现在填写路径上。

所以改成服务端重放。客户端仍然提交所有答案，服务端从第一题开始重新走：

```
当前题目 = 第一题
while 当前题目:
    如果当前题目已经访问过 -> 判定循环，报错退出
    记录到 path
    取出这道题的答案
    如果没有答案且是必答 -> 报错
    如果有答案 -> 按题型校验，通过后放进 answers
    根据校验后的答案检查 jumps，找到目标就过去
    否则按 order 进入下一题
```

代码在 `checkAnswers()` 里。这样有几个好处：

- 必答题只在真正经过的题目上检查，被跳过的题不参与。
- 客户端偷偷多传被跳过题目的答案，服务端不会存。
- 规则怎么改，前端不需要知道细节，后端算出来的路径就是最终结果。
- 测试可以直接调接口验证路径，不用打开浏览器。

返回结果里有 `answers`（入库的答案）、`path`（实际经过的题目 id）和 `errors`。有错误时整次提交失败，不会存一半。

## 4.3 循环和无效规则

如果规则配成 1 → 3、3 → 1，填写时会在这两题之间来回。服务端用 `visited` 集合检测，第二次走到同一题就报“跳转规则形成了循环，无法完成填写”，返回 400。

创建题目时的检查包括：

- 目标题目必须存在，而且属于同一份问卷。
- 不能指向题目自己。
- 选项条件的 key 必须在当前题目的选项里。
- 数字条件的运算符必须是支持的六种，比较值必须是数字。

创建时没有禁止“向后跳”。向后跳可能形成环，但检测环需要遍历整张图，而且用户可能先建规则再补题目。现在把环的检测放在提交时，配置阶段只拦明显错误的规则。第二种更复杂的图检测没有做，测试里也没有覆盖，这一点在报告的问题部分有说明。

删除题目时会执行：

```js
questions.updateMany(
  { surveyId, 'jumps.targetQuestionId': qid },
  { $pull: { jumps: { targetQuestionId: qid } } }
);
```

如果不清理，其他题目会留下一条指向不存在题目的规则。填写时 `nextQuestion` 找不到目标会退回顺序下一题，虽然不至于崩，但配置界面上会出现“已删除的题目”，所以还是在删除时清掉。

## 4.4 答案校验

四种题型分别校验，规则如下：

| 题型 | 校验内容 | 错误提示示例 |
| --- | --- | --- |
| 单选 | 必须正好一个选项，且 key 存在 | 单选题需要且只能选择一个选项 |
| 多选 | key 不能重复、必须存在；数量在 minSelect 和 maxSelect 之间 | 至少需要选择 2 个选项 |
| 文本 | 去掉首尾空格后，字数在 minLength 和 maxLength 之间 | 最多只能输入 20 个字 |
| 数字 | 必须是有限数字；integer 为 true 时必须是整数；在 min 和 max 之间 | 必须是整数 |

几个细节：

- 文本字数用 `Array.from(str).length` 算，不是 `str.length`，这样 emoji 和部分汉字不会被算成两个字符。
- 多选题如果没配 minSelect，必答题默认至少选 1 个，选答题默认 0 个；maxSelect 为空表示不限。最多选择数在创建题目时已经限制为不超过选项总数。
- 数字题选答时允许空，空值不当作 0。提交空的学生不会进入平均值统计。
- 数字校验用 `Number(raw)`，`"12abc"` 会得到 NaN 被拒绝，空字符串在进入数字转换前已经单独处理。
- 单选题提交两个 key 会直接拒绝，避免前端控件出问题时存进奇怪的数据。

题目配置也在创建时校验：选项至少两个、key 不重复、minSelect 不大于 maxSelect、minLength 不大于 maxLength、number 的 min 不大于 max，等等。配置校验放在 `normalizeQuestion()`，答案校验放在 `checkAnswers()`，两者分开，测试也好写。

## 4.5 前端也校验一次

填写页在点“下一题”时会在浏览器里做一遍同样的检查，这样用户不用等一次请求就知道哪里填错了。但服务端仍然完整校验，前端校验只是体验优化，不能当作安全边界。

前端的跳转计算和服务端用的是同一套判断逻辑，但代码是两份（`public/js/fill.js` 和 `src/services/answer-check.js`）。没有做成共享模块，原因是前端没有打包工具，直接复制一份更简单。代价是改规则时要同步改两处，这一点在报告里也记了。

## 4.6 问卷状态和截止时间

问卷有三个状态：`draft`、`published`、`closed`。

- 草稿不能填写，公开接口返回 404。
- 发布时至少要有 1 道题，截止时间不能已经过去。
- 发布后题目锁定。原因是已经有回答时改题目会让统计对不上，比如删掉一个被选过的选项，历史回答里还留着那个 key。这个限制是我在实现到一半时加的，最初没有，后来觉得不锁会留下很多脏数据。
- 关闭后不能填写，公开接口返回 403。
- 截止时间过了但状态还是 `published` 时，公开接口按截止处理，返回 403。没有做定时任务自动改状态，查询时判断就够了。

## 4.7 统计怎么算

统计没有单独存结果，每次请求现算。以一道选择题为例，聚合管道是：

```js
[
  { $match: { surveyId } },
  { $unwind: '$answers' },
  { $match: { 'answers.questionId': questionId } },
  { $facet: {
      answered: [{ $count: 'count' }],
      optionCounts: [
        { $unwind: '$answers.optionKeys' },
        { $group: { _id: '$answers.optionKeys', count: { $sum: 1 } } }
      ]
  }}
]
```

`$unwind` 先展开每次提交里的答案数组，再按题目过滤。`answered` 是作答人数，`optionCounts` 是每个选项被选了多少次。多选的一个回答会贡献多个选项计数，所以选项计数总和会大于作答人数。

百分比的分母用 `answered`，不是总提交数。原因是跳转可能让一部分人没做到这道题，用总提交数算会出现“所有选项加起来不到 100%”的奇怪结果。

数字题用 `$avg`、`$min`、`$max`，只统计 `numberValue` 不为 null 的答案。文本题直接把所有 value 取出来返回。

整份问卷的统计是遍历题目逐个调用单题统计，再拼起来。题目数量不多，这样写比一个巨大的聚合管道好读。每次请求会对每道题查一次，N 道题就是 N 次聚合；课程作业的数据量没问题，如果以后问卷很多，可以在一次聚合里按 questionId 分组。

## 4.8 匿名和重复填写

匿名是创建者在问卷级别允许的选项。填写页只有允许匿名时才显示勾选框。提交时如果要求匿名但问卷不允许，返回 400。

匿名提交把 `respondentId` 写成 null，不是保留 id 只是不显示。这样即使有人直接看数据库，也查不到是谁填的。

同一个人可以多次填写，需求里写的是“同一个人填写多次（如果允许）”。现在没有做“是否允许重复”的开关，默认允许，每次提交都是一条新的响应文档。如果第二阶段要求限制，可以加一个问卷字段，再用 `{surveyId, respondentId}` 索引查重。
