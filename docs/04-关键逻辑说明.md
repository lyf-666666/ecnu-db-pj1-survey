# 四、关键逻辑说明

这一部分写清楚三件事：跳转怎么算、答案怎么校验、统计怎么来。代码主要在 `src/services/answer-check.js`、`src/services/question-check.js` 和 `src/services/stats.js`。

## 4.1 跳转规则怎么存

每条规则挂在某道题目上，存在 `questions.jumps` 数组里。一条规则由两部分组成：`match` 是条件，`targetQuestionId` 是目标题目。

条件有两种：

```json
{ "kind": "option", "keys": ["A"], "mode": "any" }
{ "kind": "number", "op": "==", "value": 100 }
```

选项条件的 `mode` 有两种。`any` 表示选中的选项里只要有一个在 `keys` 中就算满足；`all` 表示 `keys` 里的选项必须全被选中。单选题一般用 `any`，多选题可以选 `all`，比如“同时选了苹果和香蕉就跳到第 5 题”。

数字条件支持 `==`、`!=`、`>`、`>=`、`<`、`<=`。文本框不支持跳转，需求里只要求单选、多选和数字填空。

一份题目可以配多条规则，服务端按数组顺序检查，第一条满足的生效。都不满足就按 order 进入下一题。

## 4.2 服务端重放路径

一开始我想得比较简单：前端算好下一题，提交时按顺序检查所有必答题。后来发现有问题。假设第 1 题选 A 跳到第 5 题，第 2、3、4 题都是必答，按顺序校验就会报“必答题没回答”，但这几道题根本没出现在填写路径上。

所以改成服务端重放。客户端仍然提交所有答案，服务端从第一题开始重新走：

```
当前题目 = 第一题
while 当前题目:
    如果当前题目已经访问过 -> 判定循环，报错退出
    记录到 path
    取出这道题的答案
    如果没有答案且是必答 -> 报错
    如果有答案 -> 按题型校验，通过后放进 answers
    根据校验后的答案检查 jumps，找到目标就过去
    否则按 order 进入下一题
```

代码在 `checkAnswers()` 里。这样有几个好处：

- 必答题只在真正经过的题目上检查，被跳过的题不参与。
- 客户端偷偷多传被跳过题目的答案，服务端不会存。
- 规则怎么改，前端不需要知道细节，后端算出来的路径就是最终结果。
- 测试可以直接调接口验证路径，不用打开浏览器。

返回结果里有 `answers`（入库的答案）、`path`（实际经过的题目 id）和 `errors`。有错误时整次提交失败，不会存一半。

## 4.3 循环和无效规则

如果规则配成 1 → 3、3 → 1，填写时会在这两题之间来回。服务端用 `visited` 集合检测，第二次走到同一题就报“跳转规则形成了循环，无法完成填写”，返回 400。

创建题目时的检查包括：

- 目标题目必须存在，而且属于同一份问卷。
- 不能指向题目自己。
- 选项条件的 key 必须在当前题目的选项里。
- 数字条件的运算符必须是支持的六种，比较值必须是数字。

创建时没有禁止“向后跳”。向后跳可能形成环，但检测环需要遍历整张图，而且用户可能先建规则再补题目。现在把环的检测放在提交时，配置阶段只拦明显错误的规则。第二种更复杂的图检测没有做，测试里也没有覆盖，这一点在报告的问题部分有说明。

删除题目时会执行：

```js
questions.updateMany(
  { surveyId, 'jumps.targetQuestionId': qid },
  { $pull: { jumps: { targetQuestionId: qid } } }
);
```

如果不清理，其他题目会留下一条指向不存在题目的规则。填写时 `nextQuestion` 找不到目标会退回顺序下一题，虽然不至于崩，但配置界面上会出现“已删除的题目”，所以还是在删除时清掉。

## 4.4 答案校验

四种题型分别校验，规则如下：

| 题型 | 校验内容 | 错误提示示例 |
| --- | --- | --- |
| 单选 | 必须正好一个选项，且 key 存在 | 单选题需要且只能选择一个选项 |
| 多选 | key 不能重复、必须存在；数量在 minSelect 和 maxSelect 之间 | 至少需要选择 2 个选项 |
| 文本 | 去掉首尾空格后，字数在 minLength 和 maxLength 之间 | 最多只能输入 20 个字 |
| 数字 | 必须是有限数字；integer 为 true 时必须是整数；在 min 和 max 之间 | 必须是整数 |

几个细节：

- 文本字数用 `Array.from(str).length` 算，不是 `str.length`，这样 emoji 和部分汉字不会被算成两个字符。
- 多选题如果没配 minSelect，必答题默认至少选 1 个，选答题默认 0 个；maxSelect 为空表示不限。最多选择数在创建题目时已经限制为不超过选项总数。
- 数字题选答时允许空，空值不当作 0。提交空的学生不会进入平均值统计。
- 数字校验用 `Number(raw)`，`"12abc"` 会得到 NaN 被拒绝，空字符串在进入数字转换前已经单独处理。
- 单选题提交两个 key 会直接拒绝，避免前端控件出问题时存进奇怪的数据。

题目配置也在创建时校验：选项至少两个、key 不重复、minSelect 不大于 maxSelect、minLength 不大于 maxLength、number 的 min 不大于 max，等等。配置校验放在 `normalizeQuestion()`，答案校验放在 `checkAnswers()`，两者分开，测试也好写。

## 4.5 前端也校验一次

填写页在点“下一题”时会在浏览器里做一遍同样的检查，这样用户不用等一次请求就知道哪里填错了。但服务端仍然完整校验，前端校验只是体验优化，不能当作安全边界。

前端的跳转计算和服务端用的是同一套判断逻辑，但代码是两份（`public/js/fill.js` 和 `src/services/answer-check.js`）。没有做成共享模块，原因是前端没有打包工具，直接复制一份更简单。代价是改规则时要同步改两处，这一点在报告里也记了。

## 4.6 问卷状态和截止时间

问卷有三个状态：`draft`、`published`、`closed`。

- 草稿不能填写，公开接口返回 404。
- 发布时至少要有 1 道题，截止时间不能已经过去。
- 发布后题目锁定。原因是已经有回答时改题目会让统计对不上，比如删掉一个被选过的选项，历史回答里还留着那个 key。这个限制是我在实现到一半时加的，最初没有，后来觉得不锁会留下很多脏数据。
- 关闭后不能填写，公开接口返回 403。
- 截止时间过了但状态还是 `published` 时，公开接口按截止处理，返回 403。没有做定时任务自动改状态，查询时判断就够了。

## 4.7 统计怎么算

统计没有单独存结果，每次请求现算。以一道选择题为例，聚合管道是：

```js
[
  { $match: { surveyId } },
  { $unwind: '$answers' },
  { $match: { 'answers.questionId': questionId } },
  { $facet: {
      answered: [{ $count: 'count' }],
      optionCounts: [
        { $unwind: '$answers.optionKeys' },
        { $group: { _id: '$answers.optionKeys', count: { $sum: 1 } } }
      ]
  }}
]
```

`$unwind` 先展开每次提交里的答案数组，再按题目过滤。`answered` 是作答人数，`optionCounts` 是每个选项被选了多少次。多选的一个回答会贡献多个选项计数，所以选项计数总和会大于作答人数。

百分比的分母用 `answered`，不是总提交数。原因是跳转可能让一部分人没做到这道题，用总提交数算会出现“所有选项加起来不到 100%”的奇怪结果。

数字题用 `$avg`、`$min`、`$max`，只统计 `numberValue` 不为 null 的答案。文本题直接把所有 value 取出来返回。

整份问卷的统计是遍历题目逐个调用单题统计，再拼起来。题目数量不多，这样写比一个巨大的聚合管道好读。每次请求会对每道题查一次，N 道题就是 N 次聚合；课程作业的数据量没问题，如果以后问卷很多，可以在一次聚合里按 questionId 分组。

## 4.8 匿名和重复填写

匿名是创建者在问卷级别允许的选项。填写页只有允许匿名时才显示勾选框。提交时如果要求匿名但问卷不允许，返回 400。

匿名提交把 `respondentId` 写成 null，不是保留 id 只是不显示。这样即使有人直接看数据库，也查不到是谁填的。

同一个人可以多次填写，需求里写的是“同一个人填写多次（如果允许）”。现在没有做“是否允许重复”的开关，默认允许，每次提交都是一条新的响应文档。如果第二阶段要求限制，可以加一个问卷字段，再用 `{surveyId, respondentId}` 索引查重。

## 4.9 改一道题时到底发生了什么

第二阶段最容易写错的地方是“改题”。需求的原话是：修改题目时不要影响已经做好的问卷；如果需要改，应该生成新的题目；同一题目的不同版本可以同时存在。

落到代码里，一次修改分三种入口，走的规则不一样：

| 入口 | 行为 | 版本变化 |
| --- | --- | --- |
| 题目库页面“修改” | 给 root 加一个新版本，不改任何问卷 | v1 → v2 |
| 问卷编辑页“编辑题目” | 以这道题当前用的版本为父版本，加一个新版本，只把这份问卷指过去 | v2 → v3，其他问卷仍是 v2 |
| “恢复此版本” | 把目标版本的内容复制成一个新版本，父版本指向被恢复的那一版 | v2 → v5，parent 是 v2 |

第二种是最关键的。代码在 `src/routes/surveys.js` 的 `PUT /:id/questions/:qid` 里，逻辑是：

```js
const currentVersion = existing.versionId ? await findVersion(existing.versionId) : null;
if (!currentVersion || !sameContent(currentVersion, result.doc)) {
  const version = await addVersion(root, result.doc, {
    source: 'fork',
    parentVersionId: existing.versionId || root.latestVersionId,
    changeNote: '在问卷中修改'
  });
  update.versionId = version._id;
  update.versionNo = version.versionNo;
}
```

注意 `parentVersionId` 用的是 `existing.versionId`，不是 `root.latestVersionId`。这样版本链能看出“这份问卷是从哪一版改出来的”。比如 A 卷用的是 v1，B 卷已经改到 v3，此时改 A 卷，生成的是 v4，父版本是 v1，而不是 v3。界面上会显示“由 v1 改出”。

`sameContent` 只比较题目内容，不比较 `required` 和 `jumps`。只把必答改成选答、或者调一下跳转，不应该产生一个内容完全一样的新版本，否则版本列表会被这些操作刷满。

还有一种情况是修改后的内容和父版本完全一样。现在仍然会生成新版本，因为用户点了保存，大概率是希望留一个记录。如果以后觉得版本太多，可以在 `addVersion` 前加一次内容比较，相同就跳过。这次没做，是担心出现“点了保存但没反应”的困惑。

## 4.10 已发布问卷为什么不会被改坏

这里有三个独立的保护，任何一层单独失效都不至于出问题：

1. **接口层**：`PUT /api/surveys/:id/questions/:qid` 和 `POST .../sync` 都检查 `survey.status === 'draft'`，发布后直接 400。
2. **数据层**：问卷里的题目指向具体版本 id，而版本表只增不改。即使有人绕过接口直接改题库，已发布问卷引用的那条版本文档也不会变。
3. **快照层**：`questions` 文档里存了一份完整内容。填写和统计读的是这份快照，不读版本表。所以就算版本表被改了，已发布问卷的题目和统计口径仍然一致。

发布时还会把该问卷所有题目打上 `frozen: true`。这个字段目前只是标记，没有参与权限判断，作用是让“已冻结”这件事在数据上可见，排查问题时能一眼看出来。

关掉了一个可能的坑：发布后修改题库里的题，不会自动同步到任何问卷。想让草稿问卷用上新版本，需要显式点“更新到 vN”。这个按钮会清空跳转规则，因为新版本的选项编号可能和老版本对不上，留着旧规则会指向不存在的 key。

## 4.11 跨问卷统计怎么合并

`GET /api/questions/:rootId/stats` 的做法是：

1. 找出所有引用这个 root 的 `questions` 文档；
2. 只保留当前用户名下问卷的那些；
3. 用这些题目 id 去 `responses.answers` 里筛答案；
4. 在内存里按题型累加。

没有写成一个巨大的聚合管道，原因是同一个 root 的不同版本可能有不同的选项集合，需要按题目分别做 key → label 的映射。用 JS 循环反而清楚。

合并的口径是**选项文字**，不是选项编号。原因很实际：v1 里 A 是“Java”，v2 里可能变成 A 是“Python”而 B 是“Java”。按 key 合并会把两个意思完全不同的东西加到一起。

代价是：如果某个版本把“Java”改成了“Java 语言”，统计里会出现两行。这是文字合并的固有限制，页面上没有做模糊匹配。真要做的话得给选项加一个稳定的业务编码，但那超出了这次作业的范围。

`answered` 用的是去重后的响应 id 数量，不是答案条数。一份问卷里如果同一道题出现两次（现在允许，通过复制题目实现不了，但理论上可以手动加两次），同一个人会被算两次，这是已知的小问题。

百分比的分母仍然是 `answered`，和单问卷统计保持一致。多选题的百分比加起来会超过 100%，这是正常的。

## 4.12 共享的权限判断

权限集中在 `src/services/question-catalog.js`：

```js
async function loadAccessibleRoot(rootId, userId) {
  // …查出 root
  const isOwner = root.ownerId.equals(me);
  const isShared = (root.sharedWith || []).some((id) => id.equals(me));
  if (!isOwner && !isShared) return { error: '没有权限使用这道题', status: 403 };
  return { root, isOwner };
}
```

- `loadAccessibleRoot`：能看、能用。列表、详情、建问卷时引用、统计都走这个。
- `loadOwnedRoot`：能改。修改、恢复、共享、建版本都走这个。

没有把权限写成中间件，因为权限依赖具体的 root，中间件拿不到。放在服务函数里，路由只判断返回值，出错分支很短。

一个细节：共享的是题目，不是版本。被共享的人能看到全部历史版本，也能挑任意版本用，但不能改。这是有意的，如果只能看最新版，“同一道题不同版本共存”这个需求对共享用户就不成立了。

## 4.13 题目库和题库的区别

界面上有两个容易混的概念，这里说明一下：

- **题目库**：所有题目的总称，就是 `question_roots` 里的东西。每道题都在里面，不需要手动“存进去”。
- **题库**：用户自己建的分组，类似收藏夹，对应 `question_banks` + `bank_items`。一道题可以放进多个题库，也可以一个都不放。

之所以每道手写的题也自动建 root，是为了让“跨问卷统计”和“版本管理”对所有题目都成立，而不是只对“特意存进题库的题”成立。否则用户会碰到“这道题为什么没有版本历史”的困惑。

代价是 `question_roots` 会随着题目数量线性增长，而且大部分可能只被用过一次。课程作业的量级无所谓，真实产品里可能需要一个“归档未使用题目”的清理任务。
